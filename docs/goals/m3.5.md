## Frozen Scope

M3.5 extends the existing framework-owned `Operations/AdminAccess` capability across the existing
six server layers and the generic `admin/apps/web-ele` application. It does not create a physical
module or another authentication system.

### Administrator Accounts

- List and filter administrators with explicit paging.
- Create an administrator with a server-hashed initial password and selected active roles.
- Edit the display name and role memberships.
- Activate and deactivate accounts.
- Reset another administrator's password.
- Prevent self-deactivation, self-role mutation, and operations that would leave no active built-in administrator.
- Revoke active refresh-token families when an account is deactivated or its password is reset.

### Roles And Permissions

- List roles and their effective registered permission assignments.
- Create, rename, activate, and deactivate custom roles.
- Replace a custom role's permission set using names from the runtime permission-definition catalog.
- Keep the built-in `Administrators` role active, immutable, and synchronized with all registered permissions.
- Reject unknown permission names and duplicate role names.

### Sessions

- List administrator refresh-token families without exposing token values or hashes.
- Show bounded operational metadata and revocation state.
- Revoke an exact active family and make repeated revocation safe.
- Keep access-token lifetime and existing refresh rotation semantics unchanged unless the M35-02
  security design proves a required compatible change.

### Audit

- Query administrator-access audit records with paging and bounded filters for time, action,
  success, actor, subject administrator, role, and correlation identifier.
- Audit every successful administrator, role, permission, password, and forced-session mutation in
  the same MySQL transaction as authoritative state.
- Keep secrets, passwords, token values, token hashes, request bodies, and connection strings out
  of audit data and logs.

### API And Admin

- Add explicit DTOs and thin HTTP endpoints under the existing administrator-authenticated API.
- Add stable permission and error codes, server-side authorization, optimistic concurrency, and
  idempotency where retries can create duplicate authoritative state.
- Keep OpenAPI accurate and generate the M3.5 TypeScript contracts through the frozen checked
  `@hey-api/openapi-ts` workflow rather than maintaining an unchecked duplicate model.
- Add compact Vben `web-ele` workspaces for Administrators, Roles and permissions, Sessions, and
  Audit, with route and action visibility driven by server permission codes.
- Provide loading, empty, error, unauthorized, forbidden, validation, conflict, retry, and
  confirmation states at supported desktop and mobile widths.

Detailed aggregate, transaction, endpoint, ETag, idempotency, permission, error, query, and UI
contracts are frozen in M35-02 before implementation begins. M35-02 may clarify these mechanics but

## M35-02 Frozen Domain And Security Contract

This section freezes `M35-02-T01`. Later M35-02 contracts must implement these rules without
moving them out of their authoritative owners.

### Aggregate Ownership And Revisions

- `Administrator` remains the aggregate root for immutable user name and normalized user name,
  display name, password hash, active state, created, updated and last-login UTC timestamps,
  role-membership children, and a new `Revision` starting at `1`.
- `AdminRole` remains the aggregate root for name and normalized name, immutable built-in marker,
  active state, created and updated UTC timestamps, permission-grant children, and a new `Revision`
  starting at `1`.
- Administrator creation includes its initial canonical memberships; role creation includes its
  initial canonical permissions. Initial children belong to revision `1`.
- One changed aggregate command increments its revision exactly once regardless of child deltas.
  Login-time recording does not change the management revision; password rehash does.
- Canonical target-state setters are intrinsically idempotent. If requested state already equals
  current state, no timestamp, revision, child, or audit changes, even with an older supplied
  revision. A request that changes state must match current revision or fail `RevisionConflict`.
- Self-protection and built-in-role rules are checked before an apparent no-op and cannot be
  bypassed by submitting existing state.

### Administrator Transitions

- User names never change after creation. Display names are trimmed, contain `1..128`
  non-control characters, and may be changed through a target-state transition.
- Role replacement receives unique, non-empty role IDs; an empty set is valid. Every requested
  role must exist and be active. Unchanged memberships retain evidence; removed memberships are
  deleted; new memberships receive server IDs, authenticated actor, and server UTC time.
- An administrator can never replace their own roles, deactivate themselves, or reset their own
  password. Deactivation or role replacement may never leave fewer than one active administrator
  assigned to the built-in `Administrators` role.
- Activation and deactivation are target-state setters. Deactivation revokes every active refresh
  family for the target in the same transaction. Repeated deactivation remains an aggregate no-op
  but cleans any residual active family without duplicate audit.
- Password reset receives plaintext only at the Application boundary, hashes before mutation,
  always changes the credential and revision, and revokes every target family in the same
  transaction. Plaintext is never persisted or logged. Inactive accounts may be reset;
  reactivation never restores sessions.

### Roles And Registered Permissions

- The sole built-in role is exactly `Administrators`, is always active, and never changes name or
  built-in marker. Operator rename, state, or permission replacement attempts fail
  `BuiltInRoleImmutable`, including apparent no-ops.
- A system-only seed transition synchronizes that role to the exact ordinal runtime permission
  catalog, preserves unchanged grants, delta-adds/removes, advances once only when changed, and is
  a no-op on a second run. Missing, duplicate, or malformed built-in state with existing
  administrators is `InvariantViolation`; it is not silently recreated.
- Custom role names are FormKC-normalized and trimmed, contain `1..64` non-control characters,
  and use invariant-uppercase uniqueness. Custom roles may be renamed, activated, or deactivated.
- Deactivation retains memberships and grants. Authorization ignores inactive roles, so their
  permissions stop immediately and resume after activation.
- Custom-role permission replacement accepts a unique, case-sensitive subset of registered names;
  empty is valid. Unchanged grants retain evidence; add/remove deltas advance revision once.
  Unknown names fail `UnknownPermission`. Catalog-removed names are ineffective and are pruned by
  later replacement or built-in synchronization.

### Session Families

- `RefreshTokenSession` continues to own one hashed-token row; no second store or family aggregate
  is added. A stateless domain transition operates over all transactionally locked rows with one
  `FamilyId` and requires one administrator owner.
- Family revocation changes all unrevoked rows, including expired rows, without overwriting prior
  evidence. Add `PasswordReset` and `ForcedByAdministrator`; deactivation uses
  `AdministratorInactive`.
- Unknown family fails `SessionFamilyNotFound`. A fully revoked family succeeds as a no-op and
  adds no audit. Operators may revoke their own family as a security action.
- Revocation prevents refresh but does not deny an already-issued access token during its existing
  15-minute lifetime. Database active-account and permission checks continue applying on protected
  requests.

### Policy, Audit, And Failures

- `AdminAccessManagementPolicy` owns actor/target, active built-in count, active requested-role,
  built-in identity, and registered-permission checks over transactionally locked facts.
  Application supplies authenticated actor, clock, generated IDs, catalog, and locks; clients
  never supply identity, time, counts, or authoritative permission state.
- Audit `AdministratorId` means subject and `ActorAdministratorId` means actor. Add nullable
  `SessionFamilyId` and `TargetRevision`. Add actions `AdministratorDisplayNameChanged`,
  `AdministratorActivated`, `AdministratorDeactivated`, `AdministratorPasswordReset`,
  `RoleRemoved`, `RoleRenamed`, `RoleActivated`, `RoleDeactivated`, and `SessionFamilyRevoked`.
- Emit one audit per changed aggregate transition, one membership/permission audit per delta, and
  one family audit per actually changed family. State and audit commit atomically. No-op and replay
  add no audit. Failed commands use structured logs and rolled-back evidence, not success audit.
- Audit/logs never contain passwords, token values or hashes, request bodies, signing keys,
  connection strings, or production credentials.
- Management uses `AdminAccessFailureKind`: `BadRequest`, `Unauthorized`, `Forbidden`, `NotFound`,
  `Conflict`, `UnprocessableEntity`, `InternalError`. Stable new codes are `InvalidRequest`,
  `AdministratorNotFound`, `RoleNotFound`, `SessionFamilyNotFound`, `UserNameAlreadyExists`,
  `RoleNameAlreadyExists`, `RevisionConflict`, `IdempotencyConflict`,
  `SelfDeactivationForbidden`, `SelfRoleMutationForbidden`, `SelfPasswordResetForbidden`,
  `LastActiveBuiltInAdministratorRequired`, `BuiltInRoleImmutable`, `RoleInactive`,
  `UnknownPermission`, and `InvariantViolation`. Existing authentication codes remain stable.

### Permission Definitions And Evaluation

The complete M3.5 permission set is:

| Permission | Authorized surface |
| --- | --- |
| `Operations.AdminAccess.Access` | Existing authenticated operations shell, `/api/auth/codes`, `/api/user/info`, and prerequisite for every `/api/admin-access/*` endpoint. |
| `Operations.AdminAccess.Administrators.Read` | List and inspect administrators. |
| `Operations.AdminAccess.Administrators.Manage` | Create administrators and change display name, roles, or active state. |
| `Operations.AdminAccess.Administrators.ResetPassword` | Reset another administrator's password. |
| `Operations.AdminAccess.Roles.Read` | List and inspect roles and the registered permission catalog. |
| `Operations.AdminAccess.Roles.Manage` | Create or mutate custom roles and permission assignments. |
| `Operations.AdminAccess.Sessions.Read` | List redacted refresh-token families. |
| `Operations.AdminAccess.Sessions.Revoke` | Revoke one exact refresh-token family. |
| `Operations.AdminAccess.AuditLogs.Read` | Query administrator-access audit history. |

`Access` and the endpoint leaf permission are both required and may come from different active
roles. Leaf permissions never imply `Access`, the catalog and UI never auto-add it, and `Access`
alone reveals no management route. Controller policies provide an outer guard; every Application
use case independently resolves the authenticated administrator and checks `Access` followed by
the leaf permission before normalizing target identifiers, looking up an idempotency receipt, or
querying sensitive state. An unauthenticated request returns `401`; an authenticated request
missing either permission returns `403`, regardless of target existence, request revision, or
idempotency history.

After authorization, commands execute in this order: validate and canonicalize transport input;
resolve an exact idempotent replay when applicable; acquire the frozen MySQL locks; resolve target
and related facts; enforce actor/target and built-in policy; apply revision and domain transitions;
append audit and receipt evidence; commit once. Queries authorize before validating filters and
calling repositories. Clients can therefore never use `400`, `404`, `409`, or `422` to probe a
management resource without the required permission.

### Contract Limits, Paging, And Ordering

- Every page is one-based, defaults to `Page = 1` and `PageSize = 20`, and permits a maximum page
  size of `100`. `AdminAccessPageDto<T>` contains `Items`, `TotalCount`, `Page`, and `PageSize`.
- Search and correlation filters are trimmed and limited to `128` characters. No endpoint accepts
  a client-selected sort expression or unbounded query.
- Administrator user names retain the existing `3..64` rule; display names are `1..128`; custom
  role names are `1..64`; managed passwords are `12..256` characters.
- Role-ID collections contain at most `100` unique, non-empty IDs. Permission-name collections
  contain at most `512` unique, non-empty, case-sensitive names of at most `128` characters.
  Duplicate collection values are `InvalidRequest`; the server canonicalizes accepted values by
  ordinal order before comparison or fingerprinting.
- Administrator pages order by normalized user name ascending, then identifier ascending. Role
  pages put the built-in role first, then order by normalized name and identifier ascending.
  Session-family pages order by last activity descending, then family identifier ascending. Audit
  pages order by occurrence descending, then audit identifier descending.
- Audit queries require both `FromUtc` and `ToUtc` as ISO-8601 UTC values, use the half-open range
  `[FromUtc, ToUtc)`, require `FromUtc < ToUtc`, and permit at most `31` days. Query timestamps are
  filters only and never become authoritative mutation time.

### Revisions And Strong ETags

Administrator and role responses expose a positive `Revision`. Create, detail, and mutation
responses set exactly `ETag: "<revision>"`. Every existing-administrator or existing-role command
requires exactly one `If-Match` value in that same strong, quoted, canonical positive-decimal form;
weak tags, `*`, lists, zero, negative, missing, or non-canonical values fail `InvalidRequest`.
Bodies contain no duplicate expected revision.

After all policy checks, a state-changing command whose expected revision is stale fails
`RevisionConflict`. A canonical target-state request already equal to current state succeeds with
the current DTO and ETag even when its supplied revision is older, adds no audit, and does not
increment revision. Self-protection and built-in-role policy run before no-op recognition. Password
reset always changes state, so a non-replay reset requires the exact current revision. List DTO
revisions may seed an `If-Match`, but the client must handle a concurrent `409` and must never
calculate a successor revision.

### Idempotency Receipts

`POST` administrator creation, role creation, and password reset require exactly one non-empty GUID
`Idempotency-Key` in canonical hyphenated `D` form. The durable unique scope is
`(ActorAdministratorId, CommandKind, IdempotencyKey)`. Each accepted command stores an ordinal
SHA-256 fingerprint of canonical non-secret intent, target resource ID, resulting revision, and
server UTC creation time atomically with state and audit.

The administrator-create fingerprint contains normalized user name, normalized display name, and
sorted role IDs. The role-create fingerprint contains normalized role name and sorted permission
names. The password-reset fingerprint contains target administrator ID and expected revision but
deliberately excludes plaintext, password hash, and any fast password digest. The receipt stores no
secret, request body, response body, token material, IP address, or user agent.

An accepted replay with the same non-secret fingerprint performs no mutation, hashing, revision
increment, session revocation, or audit; it returns `200`, the target's current redacted
representation, and current ETag. Reusing a key with a different non-secret fingerprint fails
`IdempotencyConflict`. For administrator creation and password reset, the first accepted secret
wins: a retry with the same key never applies another supplied password, even if that value
differs, and changing initial-password or reset-password intent requires a new key. Concurrent
matching requests serialize so exactly one mutates and the others replay. Failed commands create
no receipt.
Replay lookup occurs after authorization and canonical validation but before current-revision or
target-state evaluation, allowing a lost successful response to replay after the target advanced.

No other M3.5 command uses a receipt. Canonical aggregate setters and family revocation are already
intrinsically retry-safe and produce no duplicate audit on a repeated target-state request.

### Global Lock Order

Every write path uses one total order. A path skips resources it does not need but never reverses
these categories:

1. atomically claim and lock one idempotency receipt key when the command requires it;
2. lock the unique built-in `Administrators` role row when last-active or seed policy is involved;
3. lock all other affected role rows by ordinal GUID, then their permission rows by name and ID;
4. lock affected administrator rows by ordinal GUID;
5. lock membership rows by administrator ID, role ID, and membership ID;
6. lock refresh-token rows by family ID, creation time, and session ID;
7. append audit rows and finalize the already claimed receipt immediately before the single commit.

`SELECT ... FOR UPDATE` queries contain the matching `ORDER BY`; non-locking probes are always
re-read and validated after the ordered locks. The built-in role row is the serialization guard for
administrator active-state and role-replacement commands. Those commands lock it before counting
active administrators assigned to that role, so two concurrent commands cannot each remove one of
the last two administrators. Missing or malformed guard state fails `InvariantViolation`.

The authentication paths adopt the same order:

- login locks the normalized administrator row before password/active checks, optional password
  rehash, last-login recording, and new-family insertion, preventing a successful login from
  creating a family across deactivation or password reset;
- refresh and logout first perform a non-locking token-hash probe only to discover owner and family,
  then lock the administrator, then re-read and lock the complete family in canonical order, and
  finally revalidate exact token hash, owner, family, revocation, expiry, and account state;
- management family revocation probes the owner without exposing it, locks that administrator,
  locks the complete family, and revalidates one owner before mutation;
- administrator deactivation and password reset lock the target administrator before all of that
  administrator's families in family order.

This replaces the current token-first refresh/logout locking. No code path may hold a session lock
and then wait for an administrator or role lock.

### Command Transactions And Receipt Claim

Every command opens one transactional NovaCore unit of work over the single `NovaGameDbContext`.
State deltas, membership or permission children, forced session revocations, audits, and a receipt
commit together. Any exception, cancellation, audit failure, constraint failure, deadlock, or lock
timeout rolls the whole unit back.

Receipt commands issue one parameterized atomic
`INSERT ... ON DUPLICATE KEY UPDATE Id = Id` with a new candidate receipt ID, then select the unique
key `FOR UPDATE`. A stored ID equal to the candidate owns a new claim; a different stored ID is an
existing receipt. Existing fingerprints and target IDs are compared in constant-time where byte
data is involved. Matching receipts replay; mismatches return `IdempotencyConflict`. The candidate
contains the already known target ID and resulting revision (`1` for creates and
`ExpectedRevision + 1` for password reset). A later command failure rolls its new claim back.
Concurrent same-key requests block on the unique row; after commit one mutates and every matching
waiter replays, while after rollback one waiter becomes the new owner.

Command-specific locking is:

- administrator create: receipt, requested active roles by ID, administrator and membership
  inserts, aggregate and membership audit, receipt completion;
- role create: receipt, role and permission inserts, aggregate and permission audit, receipt
  completion; normalized-name uniqueness serializes competing names;
- display-name change: target administrator, canonical no-op/revision transition, aggregate audit;
- role replacement: built-in guard, probed union of current and requested roles, target
  administrator, target memberships, revalidation, delta and audit;
- active-state change: built-in guard, target administrator and memberships, last-active check,
  then target families for deactivation, state and audit;
- password reset: receipt, target administrator, all target families, credential/session/audit
  mutation, receipt completion;
- custom-role rename, active-state, or permission replacement: target role, then permission rows
  for replacement, state/delta audit;
- exact family revocation: probed owner administrator, complete family, changed-family audit.

Canonical no-ops write no state or audit. Receipt replays write nothing after reading current
redacted target state. Known normalized-user-name, normalized-role-name, receipt-key, and EF
concurrency constraint names translate to the T02 codes. Provider messages are never returned.
There is no provider-level automatic retry: deadlock, lock timeout, unknown unique failure, and
unexpected MySQL errors roll back and use the sanitized internal-failure path. A caller retries an
uncertain receipt command with the same key, a target-state command with the same intent, or family
revocation by exact family ID. Login and refresh are never automatically replayed.

are intentionally absent from the server

request identity. A slow response may not replace a newer filter result, ETag, selection, detail,

terminates the still-owned Job Object, verifies that it reports zero owned processes, and only then
retries `CloseHandle`; an injected-failure probe proves this path terminates a live child. Job
configuration failure uses the same verified close path, and an injected configuration-failure
probe must complete that close before returning the original failure.

The final cleanup assertion reports zero matching containers, networks, volumes, listening ports,
owned API/Vite/Playwright/browser process identities, and temporary secret/environment files.
All reporter output, test output and explicit screenshots resolve beneath
`.local/admin-management/<run-id>`. Successful evidence is removed only from that validated
absolute path; failed evidence may remain only there after all binary or compressed artifacts are
removed, raw child-process transcripts are deleted, and every retainable text artifact passes the
secret scan. Recursive removal outside that root is refused. User-owned `lefthook.yml` is never
scanned as milestone evidence, changed, staged, or removed.

On a successful browser result, the verifier validates the exact redacted response-audit reports.
The `finally` path then stops the complete Job Object process tree, drains the authenticated
dynamic-secret registry, removes Docker and temporary secrets, verifies ports and legacy outputs,
and only then decodes the exact allowlisted screenshots for IHDR bounds, dimensions, opacity,
pixel diversity, and SHA-256 identity. Immediately before retained-text scanning it rechecks each
validated PNG identity, scans exact configured and dynamic secrets plus UTF-8 and decoded-token
hash representations, and never reads child stdout/stderr into a thrown diagnostic. Only after
every check passes may it delete successful evidence. Any operation or cleanup failure uses an
empty screenshot allowlist and removes all binaries; an incomplete dynamic registry or failed
Playwright operation removes the complete run root rather than retaining possibly unscannable
text. Stopping the registry cancels only the wait for another connection: an already accepted
frame must finish or produce a protocol fault. Even after a fault, the verifier obtains a
cleanup-only snapshot of every value already accepted before scanning or deleting evidence, but
only after the collector worker has joined. A stop timeout cannot snapshot, dispose, or clear
worker-owned state. If join or snapshot completeness cannot be proved, failed evidence has no
retention fallback: only bounded, verified whole-run-root removal retries are allowed. A failed
secret scan enforces the same removal rule regardless of browser result or registry-completion
state. Real transient-lock, permanent-lock, and boundary probes verify the bounded deletion policy.
