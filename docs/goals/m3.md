grants one configured equipment item to an exact player, inspects the durable grant history, and may

inventory, or operations framework to NovaGame. It does not authorize extraction.

## Approved Behavior Boundary

`PlayerAssetsProfile` remains authoritative for owned items, equipment assignments, and revision.
Grant adds one `OwnedEquipmentItem`; rollback removes that exact owned item only when no equipment
assignment references it. A game-owned `PlayerEquipmentGrant` aggregate records the immutable grant
result and the optional one-time rollback result.

The Application layer resolves the active immutable equipment definition before opening one
SwordMaster database transaction. Inside that transaction it locks the player profile first,
coordinates the profile and grant aggregate, and persists the successful operation evidence.
Permission evaluation happens before this transaction and no NovaGame database write participates
in it.

The GET result is newest-first, paged, and includes the current player-assets revision and strong
ETag. First execution and exact replay both return `200 OK` and the same command result. Failed or
denied attempts are structured logged without tokens, reasons, request bodies, private player data,
or configuration payloads.

`/player-equipment-grants`.

dependency resolution. This is repository composition only: the generic `@vben/web-ele` app does
not import the sample. Auth/request copies required for the first game-owned composition remain
bounded and verifier-controlled; M3 records them as evidence rather than extracting a framework
shell.

The administrator OpenAPI artifact is separate from the existing player-authenticated
`player-assets.openapi.json`, which must retain only the approved player paths and player security
scheme.

- An authorized operator can grant one configured equipment item to one exact SwordMaster player.
- Exact retries return the original result without duplicate item, grant, audit, or revision changes.
- Changed idempotent requests and stale revisions fail without partial mutation.
- Rollback removes only the issued unequipped item and retains immutable operation history.
- Administrator and player credentials, permissions, APIs, and OpenAPI contracts remain isolated.
- The SwordMaster MySQL migration, permission seed, API, persistence, admin, and real browser path pass.
- Generic NovaGame server, client, and admin remain free of SwordMaster business source and policy.
- No extraction, M4 work, NovaCore change, secret, stale generated output, or disposable resource remains.
- M3 verification evidence is complete and execution is deactivated.

## Non-Goals

- Implementing bulk, scheduled, campaign, quantity, currency, mail, shop, ranking, or generic reward grants.
- Adding player search, account support, item transfer, item consumption, expiry, approval chains, or a catalog API.
- Auto-equipping a granted item or auto-unequipping an item during rollback.
- Moving PlayerAssets, equipment, grant policy, administrator pages, or game contracts into NovaGame.
- Extracting a generic operations, rewards, inventory, or admin-shell mechanism during M3.
- Promoting the experimental GameConfig validator contract or starting M4.
- Modifying NovaCore.
